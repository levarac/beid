# AGENTS.md

## Repo overview

beid is a native iOS SwiftUI app (no Flutter) that turns BLE mutual
observations at real-world events into portable attendance proofs. The
Xcode project is generated by XcodeGen from `ios/project.yml` into
`ios/Beid.xcodeproj` — do not hand-edit the `.xcodeproj`, edit `project.yml`
and run `xcodegen generate` from `ios/`. The simulator has no BLE radio, so
`SensingCoordinator` runs a scripted `DemoEvent` mode there instead of real
scanning (see `ios/README.md` "DemoEvent mode"); the Barnard BLE SDK
(`ios/Vendor/Barnard`) is vendored verbatim from `levarac/barnard`, not a
remote SwiftPM dependency (see `ios/README.md` "Barnard SDK dependency" for
why).

## Localization Process

- **Source language**: English (`en`). All user-facing strings are authored
  in English in code; `ios/project.yml`'s `options.developmentLanguage` is
  `en` and is the single source of truth for the development region — do
  not set a development region anywhere else.
- **Target locales**: `en` (source) + `ja`, `zh-Hans`, `es`, `fr` — 5 locales
  total. **PROPOSAL — Ken ratification pending**: Ken's instruction was
  "主要5ヶ国語くらい" (roughly 5 major languages), so this exact non-`en` set
  (Japanese, Simplified Chinese, Spanish, French) may still change. Treat
  the locale list in `Localizable.xcstrings` as the canonical current set;
  this doc's list must match it.

### Mechanism

- **SwiftUI String Catalogs** (`Localizable.xcstrings`), one per target,
  living next to the target's sources (e.g.
  `ios/Beid/Localizable.xcstrings` for the `Beid` target). Xcode
  auto-extracts strings from `Text("...")` and `String(localized:)` call
  sites into the catalog on build — you do not hand-maintain key lists.
- **MUST:** Design-system components that display localizable text take
  `LocalizedStringKey`, never `String`. Genuinely dynamic runtime data must
  use an explicitly named verbatim API so it cannot be mistaken for copy.
- **Key conventions** — two allowed forms, chosen by reuse:
  - **Literal English sentence as key** (the default, e.g.
    `Text("Get Started")`) for one-off view copy that appears in exactly one
    place. Cheapest to write and read; if the English changes, the key
    changes with it, which is correct for text with no reuse.
  - **Explicit reverse-DNS-ish key** via
    `String(localized: "welcome.cta.title", defaultValue: "Get Started")`
    for strings that are reused across views, or that are parameterized
    (interpolated values, plurals). Reason: a literal-English key that
    contains a `%@`/`%lld` placeholder is fragile — editing the surrounding
    English sentence silently orphans every existing translation of it,
    because the key *is* the sentence. An explicit key decouples the
    translation unit's identity from its current English wording, so
    translators' work survives English copy edits.
  - Rule of thumb: if you're about to write the same `Text("...")` in a
    second place, or the string takes an interpolated argument, switch it
    to an explicit key.
- **Translator context**: every string whose meaning isn't obvious from the
  English alone (short button labels, ambiguous nouns, anything with a
  placeholder) gets a `comment:` — e.g.
  `String(localized: "Seal", comment: "Verb: the user's action to finalize and store a collected proof, not a noun/wax-seal reference.")`.
  Comments are for translators, not developers; state what the word means
  or does in context, not why the code is structured the way it is.
- **Pluralization**: use String Catalog plural variants (`.stringsdict`-style
  variation keyed by `plural`), not manual `count == 1 ? ... : ...` string
  branching in Swift. Author the base string with a `%lld` (or `%d`)
  placeholder and let each locale supply its own plural rule in the
  catalog — some target locales (e.g. `ja`, `zh-Hans`) have no plural forms
  and just need the `other` variant filled.
- **Never concatenate localized fragments.** `Text(a) + Text(" ") + Text(b)`
  or string-concatenating two `String(localized:)` results breaks word
  order and grammar in most target locales. Compose one full sentence per
  string, using format specifiers for the parts that vary.
- **Format specifiers use positional arguments** for any string with more
  than one interpolated value, e.g.
  `String(localized: "%1$@ found %2$d nearby peers", ...)`, not positional
  `%@ %d` — different locales may need to reorder the arguments in
  translation, which positional specifiers allow and bare ordinal ones
  don't.

### Agent workflow

When an agent adds or changes user-facing copy:

1. Write the English string in code (literal or explicit key, per the rule
   above), with a translator `comment:` if the meaning isn't self-evident.
2. Build the target once (`xcodebuild build` or an Xcode build) so Xcode
   syncs the new/changed key(s) into `Localizable.xcstrings`.
3. In the same PR, fill translations for all target locales in the
   catalog. A machine-drafted translation is acceptable as a starting
   point, but every machine-drafted entry MUST be left in (or set to) the
   catalog's `needs_review` state, not `translated` — `needs_review` is the
   explicit marker that a human/translator pass is still owed.
4. Add this line to the PR description checklist:
   `- [ ] Localized strings: all target locales present in Localizable.xcstrings (needs_review OK, missing OK, broken key NOT OK)`

**Untranslated strings fall back to English automatically** (standard
String Catalog / `Bundle.localizedString` behavior) — a locale missing a
translation for a given key is never a crash or a build failure, only a
review item to close out later. This is what makes "translate in the same
PR, machine-draft acceptable" safe: an incomplete translation degrades
gracefully to English rather than blocking or breaking the build.

### Testing

- Run the app under a specific language without changing the system
  language: Xcode scheme editor → Run → Options → **App Language**, or from
  the CLI, launch args `-AppleLanguages (ja) -AppleLocale ja_JP`.
- Check **`ja`** specifically for truncation — CJK glyphs and English-length
  assumptions interact badly, and `ja` is often among the longest
  string-length outliers in this string set (e.g. header labels, primary
  CTAs).
- Also check the **pseudo-locale double-length** case (a string catalog
  variant or debug locale with every string doubled in length, no real
  translation) to catch truncation/wrapping bugs independent of any one
  real language's actual translation quality.
- Check **Dynamic Type** interaction: enable a large accessibility text
  size (Settings → Accessibility → Display & Text Size → Larger Text) while
  on a longer-string locale (`ja` or pseudo-locale) — the two axes compound
  and surface truncation that neither alone would.

### What NOT to localize

- **DemoEvent fixture data** (event names, fake peer labels, etc. in
  `ios/Beid/Models/DemoEvent.swift` and friends): localize it. Recommendation
  is to treat DemoEvent strings as regular user-visible copy, not internal
  test fixtures — DemoEvent is also the intended App Review demo path (see
  `ios/README.md` "DemoEvent mode"), so a reviewer running the app in a
  non-English App Store locale sees DemoEvent's strings as real product
  copy, not placeholder text. Do not special-case DemoEvent strings out of
  the catalog.
- Debug-only / developer-facing strings (console logs, `#if DEBUG` internal
  labels, SwiftUI `#Preview` titles) are not user-facing and are not part of
  the target locale set.

### Relationship to DESIGN.md

`DESIGN.md` (design-system contract; landing separately, see its §15
"Copywriting Voice") owns tone and vocabulary in **English** — word choice
("collected"/"sealed", never "minted"), sentence case, no exclamation marks,
the forbidden-term list (`NFT`, `token`, `on-chain`, `gas`, `mint`,
`airdrop`, `web3`), and the error-message formula. Translations MUST
preserve the *register* DESIGN.md establishes (quiet, precise, no
overclaiming) even though the literal forbidden-term list is
English-specific — each target locale needs its own equivalent-term check
(e.g. the "mint" ban maps to `鋳造`/`ミント` in `ja`, not just the English
string "mint"). When DESIGN.md and this section conflict on copy tone vs.
mechanism, DESIGN.md governs tone/vocabulary and this section governs the
localization mechanism — they are not meant to overlap.

## Delivery / CI contract (Xcode Cloud)

The full delivery doc is `docs/xcode-cloud.md` (canonical, carries
verification dates). The contract every agent must know before touching
delivery files:

- **"Ship a TestFlight test build" = update `what_to_test.json`** (repo
  root). Changing this file on any branch push both **triggers** the
  Internal Build workflow and becomes the tester-facing "What to Test"
  notes. Rewrite it wholesale each time — what to check in *this* build
  only, 1-3 plain sentences per locale (ASC locales: `en-US`, `ja`,
  `zh-Hans`, `es-ES`, `fr-FR`), no PR numbers, no internal jargon, no
  accumulated history.
- **`release_notes.json` is App Store "What's New" copy.** On non-release
  branches it is never delivered to testers and editing it neither
  triggers nor annotates test builds. Caveat: on `release/*` branches the
  current `ci_post_xcodebuild.sh` sources TestFlight notes from
  `release_notes.json` instead (a legacy pattern slated for revision in
  issue #55 — the sister project that originated it abandoned it after
  shipping stale tester notes for 19 hours through exactly this file
  confusion). When in doubt, the file you want is `what_to_test.json`.
- **Versioning**: `MARKETING_VERSION` lives once in `ios/project.yml`
  (the project is xcodegen-generated — never hand-edit the `.xcodeproj`).
  Build numbers are managed by Xcode Cloud (build number = run number);
  do not set or bump `CURRENT_PROJECT_VERSION` in the repo.
- **"Uploaded" ≠ "delivered"**: a build can be `VALID` in App Store
  Connect yet reach no tester. Internal builds auto-deliver to the "Dev"
  TestFlight group via the ASC workflow post-action; verify group
  assignment through `GET /v1/betaGroups/{id}/builds` (the reverse
  direction reads empty for internal groups).
- **ASC GUI is the source of truth for workflow settings** — they are not
  in this repo and can drift from the docs. When observed behavior
  contradicts `docs/xcode-cloud.md`, trust App Store Connect, then update
  the doc with a new verification date.
- Release-branch conventions (`release/X.Y.Z` stabilization branches,
  version rules, CI guards) are being established in issue #55 — read it
  before doing release work.
- **Code signing / team ID**: `DEVELOPMENT_TEAM` in `ios/project.yml` is
  the maintainer's personal Apple Developer team. To build on a device
  with a different account, change the team locally (Xcode signing pane
  or a local `project.yml` edit + `xcodegen generate`) — but **never
  commit a team-ID change**. PRs that touch `DEVELOPMENT_TEAM`, bundle
  identifiers, or signing settings are rejected unless the maintainer
  authored them.
