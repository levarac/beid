## 前提条件 — これを満たさないと測定が無意味になる

### 全端末を同一ビルドに更新する(必須)

`#226` でイベントコードの正規化を `shared/` へ移した(2026-08-20、`eadbf2b`)。
**旧ビルドと新ビルドで同じ大文字の文字列を打つと、別のイベントとして扱われ互いを検知しない**
(旧 `ETHTOKYO` / 新 `ethtokyo`)。

ビルドが混ざったセッションは、**エラーを出さずに無意味な結果を返す**。
「検知しない」という観測が、測ろうとしている現象なのか更新漏れなのか区別できなくなる。

**開始前に、全端末で TestFlight のビルド番号を読み上げて一致を確認すること。**

### イベントコードは全端末で同一の文字列にする

正規化が入ったので大文字小文字と前後の空白は吸収されるが、**それに頼らない**。
1 人が読み上げ、全員が同じものを入力する。

### 記録中画面の診断行を読めるようにしておく

`#218` の切り分けのため、記録中画面に

```
診断: 識別済み ◯ · 未識別 ◯
```

が出る(`#if DEBUG` で塞いでいないため TestFlight ビルドで見える)。
**これは相互確認の数ではない。** 意味は下記のとおり。

| 表示 | 中身 | 意味 |
|---|---|---|
| 識別済み | `devicesVerified` | 近接識別子(RPID)を display ID まで解決できた distinct な端末数 |
| 未識別 | `unidentifiedRpidCount` | 観測はしたが display ID に解決できなかった近接識別子の数 |

## 手順 A — #218:閾値到達の非対称の切り分け

**問い**: 2026-08-17 の検証で 4 台中 2 台が EventFound で停滞したのはなぜか。

3 つの仮説があり、**対処が正反対**なので切り分けが要る。

| 観測 | 示唆される原因 |
|---|---|
| 未識別が伸び、識別済みが伸びない | **電波は届いているが端末を同定できていない** |
| 両方とも伸びない | **そもそも受信していない**(advertise/scan の非対称) |
| 識別済みが伸びるが閾値到達が遅い | ウィンドウ境界でのカウンタのリセット |

### やること

1. 4 台以上を同じ場所に置き、全台で同じイベントコードを入力してセンシングを開始する
2. **各台の診断行を、開始から 1 分ごとに 10 分間、そのまま書き取る**(スクリーンショットでよい)
3. 停滞した台があれば、その台の 2 つの数字を特に記録する
4. 停滞が解消した場合、**何をした直後か**を記録する(アプリを開き直した / 時間が経った / 端末を近づけた)

### 記録すべきこと

- 端末の機種と OS バージョン(**古い端末ほど効く**可能性がある)
- 各台の識別済み / 未識別の推移
- 記録開始(`.recording`)に到達した台と、しなかった台
- 端末どうしの物理的な距離と、間に何があるか(体・鞄・机)

## 手順 B — #140:画面ロック時の相互観測成立率

**問い**: 「ポケットに入れたままでも相互観測が続く」というプレスリリースの体験は成立するか。

**一度も測っていない。** BLE の background mode 宣言は済んでいるが、実機データが無い。
デモ台本をフォアグラウンド前提にするかの判断材料でもある。

### 3 条件を順に測る

手順 A と**同じセッションの中で**、条件だけ変えて続けて測れる。

| 条件 | やること |
|---|---|
| ① 両方フォアグラウンド | 全台で画面を点けたまま、beid を前面に出して 5 分 |
| ② 片方ロック | 半数の端末を画面ロックし(ポケットに入れる)、5 分 |
| ③ 両方ロック | 全台を画面ロックし、5 分 |

各条件の**終わりに**画面を戻し、診断行と記録の積み上がりを読み取る。

### 記録すべきこと

- 各条件での識別済み / 未識別の**増分**(条件開始時との差)
- ロック中に記録が止まったか、続いたか
- ロック解除直後に一気に増えるか(=溜めて処理している)、それとも増分が小さいか(=止まっていた)
- iOS のバックグラウンド動作は端末の状態(充電中か、低電力モードか)に影響されるため、**それも記録する**

### この測定が答えるべきこと

- [ ] デモで「ポケットに入れたまま」を見せられるか
- [ ] 見せられない場合、台本をフォアグラウンド前提に書き換えるか

## 手順 C — gh#250:MetaMask の connect → sign → return(リリースゲート)

**問い**: WalletConnect(Reown)を除去し MetaMask を `#if DEBUG` から解放して
Release へ昇格させた(#250、DECISIONS 2026-08-21 「#250 で MetaMask を
Release へ昇格させる」)。しかし MetaMask の connect → `personal_sign` →
beid への自動復帰の往復は、**この時点まで一度も実機で検証されていない**。
Simulator では相手アプリ(MetaMask Mobile)が存在しないため原理的に検証
できない。

**これはリリースゲートであり、合否がそのまま出荷判断になる。** DECISIONS
2026-08-21 が付した実行条件そのものであり、任意の確認事項ではない。
**検証されないまま TestFlight を越えて出荷判断に進んではならない。**

> **⚠️ 2026-08-28 更新 — Fail 時の退路はもう存在しない。**
> この手順書は当初「Fail すれば MetaMask 昇格を撤回し Coinbase 1 択の
> Release 構成に戻す」と書いていた。**その退路は 2026-08-27 に消えた。**
> gh#270 で Coinbase Wallet アプリの Base への統合により接続承認ダイアログが
> 出なくなり、原因の SDK は 2025-06 以降更新停止、公式後継も native iOS の
> 移行手順が未公開だったため、PR #271 / #275 で **Coinbase SDK を完全に削除**
> した(DECISIONS 2026-08-27)。
>
> したがって **MetaMask は現在、唯一のウォレット経路である。** Fail は
> 「もう一方に戻す」ではなく「**出荷ビルドに動くウォレット機能が存在しない**」
> を意味する。合否の重みが変わっているので、Fail の場合は撤回先を選ぶのでは
> なく、**ウォレット機能の扱いそのものをオーナーに諮ること。**

### 前提条件(この手順専用)

- 実機 1 台に、検証対象ビルドの beid と、App Store 版の MetaMask Mobile の
  両方をインストールする。connect/sign 自体は同一端末上の `beid://mmsdk`
  deep link 往復であり、複数台の相互センシングとは無関係
- MetaMask 側にテスト用ウォレットを 1 つ用意する。本番資産を保持する
  ウォレットは使わない

#### ③(署名の往復)に到達する経路 — 2026-09-03 追記

**`personal_sign` を出すのは `EventBindingSheetView` だけである**
(`requestPersonalSign` / `connectAndSign`)。オンボーディングのウォレット
接続画面は `connect()` しか呼ばず、署名しない。そして binding シートが出るのは
`bindingState = .pendingConnect` のとき、すなわち **`Recording` に確定した
とき**である。

**したがって ③ は「1 台でできる」とは限らない。** 到達経路は 2 つ:

| 経路 | 条件 | 何を検証できるか |
|---|---|---|
| **実機 3 台以上**(閾値 `eventConfirmThreshold` = 3 を越える) | 手順 A と同じセッションで到達する | **Release / TestFlight ビルドそのもの**。#250 のゲートはこれについてのもの |
| **1 台 + DemoEvent モード** | **DEBUG ビルド**を実機へ入れ、`-beid-demo-event` 付きで起動(`ios/README.md` の DemoEvent mode 節)。デモは `bindingState` を `.pendingConnect` まで駆動するが**接続と署名は自動化しない** | 往復の**機構**(`MetaMaskConnector`、deep link)。**Release 成果物そのものではない** |

**4 台ある場合は前者を使うこと。** 手順 A の 10 分で `Recording` に到達するので、
その直後に同じセッションで ③ を実施できる。**A のスクリーンショットを撮り
終えてから**行う(1 台の前面がシートで塞がるため)。

#### ⚠️ "Simulate binding (Demo)" ボタンを押してはならない

`#if DEBUG` の「Simulate binding (Demo)」は **`DemoWalletConnector` を使う**。
固定のデモ鍵で署名する開発用の抜け道であり、**MetaMask を一切通らない。**
これで成功しても ③ の Pass にはならない。**binding シートでは MetaMask を
選ぶこと。**

### やること

1. beid を起動し、ウォレット選択で MetaMask を選ぶ
2. MetaMask アプリへ deep link で遷移し、接続を承認する → beid へ自動復帰
   することを確認する
3. beid・MetaMask の一方または両方をコールドスタートさせた状態から同じ
   往復をもう一度行う(コールドスタート跨ぎでの復帰を個別に確認する)
   —— **2026-09-03 実施済み**
4. 署名要求(`personal_sign`)まで進め、MetaMask 側で承認し、beid へ自動
   復帰して署名が反映されることを確認する
5. 自動復帰が起きなかった場合、どこで止まったか(MetaMask 側で止まった /
   beid に戻らなかった / 戻ったが状態が反映されなかった)を記録する

### 記録すべきこと

- 実施した端末の機種と OS バージョン、MetaMask Mobile のバージョン
- 各ステップの成否(コールドスタートの有無別)
- 失敗した場合、失敗の性質(承認画面が出ない / redirect が戻らない / 署名
  が反映されない、など)

### 合否の意味

- **Pass**: connect → sign → beid への自動復帰が、両アプリのコールド
  スタートを含めて確実に成立する
- **Fail**: 上記のいずれかが再現性を持って成立しない。**Fail の場合、結果を
  gh#250 にそのまま貼ったうえで PM / オーナーに判断を仰ぐこと** — この手順を
  実施した担当者が独断で判断しない。**なお差し戻し先は存在しない**(上記の
  2026-08-28 更新を参照)ため、諮るべきは「どちらのウォレットにするか」では
  なく「ウォレット機能を出荷対象にできるか」である

### 部分的な確認では Pass にならない

上の 3 ステップは**別々の失敗モード**を見ている。接続だけが通ったことは、
署名の往復が通ることを意味しない。特に:

- **接続の往復**(手順 2)と**署名の往復**(手順 4)は別の deep link 往復で
  あり、後者だけが `personal_sign` の応答を beid の状態へ反映する
- **コールドスタート跨ぎ**(手順 3)は、両アプリが常駐している状態では
  観測されない。常駐状態でだけ通る実装は、実利用で落ちる

**3 つすべてが確認できるまで、この行を Pass として扱わないこと。**
