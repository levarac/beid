# イベント主催者向け画面のアーキテクチャ検討（ドラフト v0.1）

> **位置づけ**: `docs/operational-flow.md` の主催者タッチポイントを踏まえた叩き台です。MTG議事録（2026-07-09、宿題「イベント主催者向け画面のアーキテクチャ検討」`01:38:47`〜`01:40:51`）は**未決着**と明記しており、本書はチームが 10 分で裁定できる状態に論点を整理するためのものです。ここに書かれた「推奨」は AI エージェント（flow-docs）の提案であり、チームの決定ではありません。

---

## 1. 論点：3つの選択肢

MTG で挙がった3案（議事録 `01:38:47`〜`01:40:51`、いずれも結論に至らず）:

| 選択肢 | 内容 |
|---|---|
| **A. 専用アプリ入口** | 主催者専用の別アプリ（別バイナリ）を用意する |
| **B. Web専用コンソール** | ブラウザで動く管理画面のみを用意し、モバイルアプリは持たない |
| **C. ユーザーアプリ内「主催者モード」** | 参加者用アプリと同一バイナリに、ロール切り替えで主催者機能を出す |

---

## 2. 運用フローのタッチポイントに対する評価

`docs/operational-flow.md` から、主催者が実際に手を動かす箇所を5つ抽出しています。それぞれについて3案がどう振る舞うかを見ます。

### 2.1 イベント登録（§2.1）

イベントID・`EventCode`・N閾値などの設定。BLE や端末ネイティブ機能は不要、フォーム入力とバックエンドAPI呼び出しで完結する。**3案とも技術的には可能**。

### 2.2 eventAuth デスク発行（§2.2）

texts#2 の推奨フロー（スタッフ端末が参加者QRをスキャン → desk key でローカル署名）は、**ネットワーク断でも止まらないオフライン署名**と**発行1件ごとのスタッフの目視操作**が要件（whitepaper §5.1「check-in desk is part of the security boundary」）。これは:
- カメラでのQRスキャン
- desk key の安全な保管とローカル署名（秘密鍵をブラウザに置くのは望ましくない）
- オフライン時のログのハッシュチェーン管理

を要求する。**Web専用コンソール（B）は、ブラウザの制約（秘密鍵管理・オフライン動作の弱さ・カメラAPIの実装差）でこの要件を満たしにくい。** A（専用アプリ）・C（アプリ内モード）は同等にネイティブ機能を使えるため要件を満たせる。

### 2.3 イベント中の監視（§2.3、texts#5 (e) W4 のダッシュボード）

texts#5 が提案する「heartbeat も申告もないのに `orphanRpidSignal` が立っている」状況をイベント中にフラグするダッシュボード（SHOULD、v1.1でMUST化検討）。これはバックエンドが集計したデータをリアルタイムに表示するだけの機能で、**BLEもネイティブ機能も不要**。3案とも可能だが、**Bが最も低コストで実装できる**（データの可視化はブラウザが最も得意な領域）。

さらに、`docs/operational-flow.md` §2.3 の**主催者側 BLE アナウンス発信**（barnard `spike/eventcode-discovery`、EventCode レス join の GATT アナウンス）が採用される場合、主催者端末は BLE peripheral advertise（GATT サーバとして振る舞う）を継続する必要がある。**Web Bluetooth API はペリフェラル（アドバタイズ）モードを提供しておらず、特に iOS Safari では BLE 自体が使えない。** これは B を実質的に不可能にする制約であり、⚠️未決の EventCode レス join 方式（`operational-flow.md` §2.3・§5 の未決3）が採用されるかどうかで B の実行可能性が変わる。

### 2.4 ファイナライズトリガー（§2.4）

`operational-flow.md` §5 未決11 の通り、トリガーが自動発火か主催者手動かは未確定。**手動トリガーだとすれば、これはボタン1つのAPI呼び出しであり3案とも可能。BもEに強い**（管理画面からのボタン操作は Web の得意領域）。

### 2.5 救済・異議対応（§2.5、texts#5 (d) appeal 裁定）

主催者が appeal を裁定するフロー（証拠パッケージの確認 → `AppealStatement` 発行）。証拠の閲覧・承認操作であり、**BLEやネイティブ機能は不要**。3案とも可能で、**Bが最も低コスト**。

## 3. トレードオフ表

評価軸: 開発コスト / 実会場での運用実態 / セキュリティ面 / オフライン挙動

| | A. 専用アプリ入口 | B. Web専用コンソール | C. ユーザーアプリ内「主催者モード」 |
|---|---|---|---|
| **開発コスト** | 高（別バイナリを2プラットフォームでゼロから構築・維持。beid は既にネイティブ作り替え中で、3本目のアプリを増やす余力への疑問符） | 低（単一のWebアプリ、既存のバックエンドAPIに乗せやすい） | 中（既存コードベースに機能フラグ/ロール切替UIを足す。barnard SDK・センシングエンジンは参加者アプリと共有できる） |
| **実会場での運用実態** | 主催者/スタッフが別アプリをインストールする手間。ETHGlobal のような一時イベントでは端末調達・インストール導線がボトルネックになりうる | eventAuth デスク発行・BLEアナウンス発信ができない（2.2・2.3参照）ため、**登録・監視・appeal専用の補助ツールにしかなれない** | 参加者と同じアプリなので追加インストール不要。ただしUIが「参加者用」と「主催者用」で混在し、誤操作防止のロール分離UXが必要 |
| **セキュリティ面** | desk key・authority 鍵などの機微情報が主催者専用バイナリに閉じる。攻撃対象面は参加者アプリと分離される | ブラウザでの秘密鍵管理はネイティブより弱い（2.2参照）。デスク発行機能を持たせるなら特に懸念 | 主催者権限のロジックが全参加者に配布される同一バイナリ内に同居 → リバースエンジニアリングで desk key ロジックや管理者APIの呼び出し規約が露出するリスクが A/B より高い |
| **オフライン挙動** | 良好（ネイティブ、desk key ローカル署名・BLE共にフル対応） | 弱い（デスク発行のオフラインfallback、BLEアナウンス共に非対応。テザリング/Wi-Fi前提の運用になる） | 良好（A と同等。ネイティブ機能を共有） |

## 4. 推奨

**C（ユーザーアプリ内「主催者モード」）を、BLE・オフライン署名が絡むタッチポイント（eventAuth デスク発行、EventCode レス join のアナウンス発信）の担い手として推奨する。** 加えて、イベント登録・監視ダッシュボード・appeal 裁定のような**BLE 非依存の管理系タッチポイントには、C と並行して軽量な Web 管理画面を持つことを妨げない**（これは A/B/C のいずれとも独立に足せる、低コストな補完）。

### 理由

1. **desk key のローカル署名と BLE peripheral advertise は本質的にネイティブ機能**であり、B（Web専用）はこの2つの主要タッチポイントで実行不可能に近い（§2.2・§2.3）。B を主線にすると「デスク発行だけ別のネイティブアプリで」という結局 A か C が必要になる二重構成に戻る。
2. A（専用アプリ）は C と同じネイティブ能力を持てるが、**beid は今まさにネイティブへの作り替え中**（MTG決定3）であり、そこにもう1本の別バイナリを追加するコストは、既存のセンシングエンジン（barnard）・鍵管理コードを再利用できる C に対して正当化しづらい。ETHGlobal のような一時イベントでは「主催者側のスタッフが専用アプリを別途インストールする」導線コストも実運用上の障害になりやすい。
3. C の弱点（同一バイナリに管理者権限ロジックが同居するセキュリティ面）は、**desk key を端末のセキュアストレージに保持しロール切替をサーバ側の認可と紐付ける**（主催者アカウントでログインしないと主催者モードのUIすら出ない、など）実装上の対策で軽減可能で、ゼロから別アプリを作るコストほどではない。

### この推奨が変わる条件（評価が変わる証拠）

- **EventCode レス join（`operational-flow.md` §2.3 未決3）が不採用になり、EventCode 配布が QR/手入力のような非BLE手段に確定した場合**、主催者側の BLE peripheral advertise 要件が消え、B（Web専用）の実行可能性が大きく上がる。この場合はデスク発行のみネイティブ（A/C）に残し、それ以外を B に寄せるハイブリッドが再検討に値する。
- **desk key のローカル署名要件そのものが緩和され（例: オンライン署名のみを許容し、オフラインfallbackを廃止）**、常時ネット接続が前提になる会場運用が確定した場合、Bでもデスク発行が現実的になりうる。
- **主催者=参加者ではないケース（自分は参加せず運営のみ行うスタッフ）が主流になる**（現状の ETHGlobal 想定では主催者/スタッフも参加者を兼ねることが多いと推定されるが未確認）場合、Cの「参加者アプリと同居」のメリットが薄れ、Aの独立性が相対的に有利になる。

## 5. ⚠️未決（このドキュメントの範囲での）

- 主催者と参加者の役割の重なり具合（主催者は自分も参加者としてセンシングするのか、運営専任なのか）が MTG議事録に明記されておらず、本書の推奨2・3の根拠に影響する仮定として残っている。
- `operational-flow.md` §2.3 の EventCode レス join 方式（完全サイレント自動参加 vs ワンタップ確認 vs 従来の手入力）の裁定が、本書 §4「推奨が変わる条件」の1点目に直結するため、本書と合わせて裁定するのが効率的。
- desk key の保管方式（デバイスのセキュアエンクレーブ/Keystore 利用か、それ以外か）は未検討。C 案採用時のセキュリティ対策として次の設計論点になる。
- ファイナライズトリガーの自動/手動（`operational-flow.md` §5 未決11）が手動の場合、そのボタンをどの画面に置くか（主催者モードUI か 補完Web管理画面か）は本書では未裁定。
